# GPS to FDM design for Betaflight 2025.12.x

## Scope

This design adds a Gazebo NavSat sensor to the vehicle, subscribes to its
`gz.msgs.NavSat` output in the bridge, and writes the result into the existing
144-byte Betaflight FDM packet. The first supported firmware line is
Betaflight `2025.12.x` (the release formerly called 4.6).

No FDM packet extension is required. Betaflight 2025.12.x already treats the
FDM position and velocity arrays as virtual GPS data when `USE_VIRTUAL_GPS` is
enabled, as it is for the SITL target.

## Data flow

```text
Gazebo world spherical origin
             |
             v
NavSat sensor on X3/base_link
             |  gz.msgs.NavSat
             v
GazeboStateSubscriber / SensorSnapshot
             |
             v
FdmBuilder: position_xyz + velocity_xyz
             |  UDP 9003, fdm_packet
             v
Betaflight 2025.12.x setVirtualGPS()
             |
             v
GPS fix, position, speed and course in Betaflight
```

## Exact FDM field meanings in Betaflight 2025.12.x

The names `position_xyz` and `velocity_xyz` are historical. In virtual GPS
mode, Betaflight 2025.12.x interprets them as follows:

| FDM field | Required value | Unit | Gazebo `gz.msgs.NavSat` field |
|---|---|---:|---|
| `position_xyz[0]` | Longitude | degrees | `longitude_deg` |
| `position_xyz[1]` | Latitude | degrees | `latitude_deg` |
| `position_xyz[2]` | Altitude above mean sea level | m | `altitude` |
| `velocity_xyz[0]` | East velocity | m/s | `velocity_east` |
| `velocity_xyz[1]` | North velocity | m/s | `velocity_north` |
| `velocity_xyz[2]` | Up velocity | m/s | `velocity_up` |

Betaflight calculates these derived GPS values:

```text
ground speed = sqrt(East^2 + North^2)
3D speed     = sqrt(East^2 + North^2 + Up^2)
course       = atan2(East, North), normalized to 0..360 degrees
```

Course is therefore measured clockwise from North: North is 0 degrees, East
is 90 degrees, South is 180 degrees, and West is 270 degrees.

The remaining FDM fields retain their existing meanings. In particular,
`pressure` remains the virtual barometer input and is independent of the GPS
altitude stored in `position_xyz[2]`.

## Gazebo setup

### 1. Define the world's geographic origin

Every world that uses NavSat must contain spherical coordinates. Use an ENU
world frame and a real WGS84 origin:

```xml
<spherical_coordinates>
  <surface_model>EARTH_WGS84</surface_model>
  <world_frame_orientation>ENU</world_frame_orientation>
  <latitude_deg>32.0853</latitude_deg>
  <longitude_deg>34.7818</longitude_deg>
  <elevation>0</elevation>
</spherical_coordinates>
```

The repository's `worlds/baylands.sdf` already provides a spherical origin.
The quadcopter worlds will need one added if GPS is enabled in them.

### 2. Load the NavSat system

Add the NavSat system plugin to the world alongside the existing IMU and
Altimeter systems:

```xml
<plugin
  filename="gz-sim-navsat-system"
  name="gz::sim::systems::NavSat"/>
```

### 3. Add a NavSat sensor to the vehicle

Add the sensor to `X3/base_link` in the vehicle model:

```xml
<sensor name="navsat" type="navsat">
  <always_on>true</always_on>
  <update_rate>10</update_rate>
  <topic>navsat</topic>
</sensor>
```

Ten hertz is a realistic starting point for GPS. The bridge may continue to
send the complete FDM packet at its configured 500 Hz; between NavSat updates,
it reuses the latest GPS sample.

### 4. Confirm the Gazebo topic

Start the world and inspect the resolved topic name:

```bash
gz topic -l | rg navsat
gz topic -e -t /navsat
```

The second command should show `latitude_deg`, `longitude_deg`, `altitude`,
`velocity_east`, `velocity_north`, and `velocity_up`. If Gazebo scopes the
topic under the world, model, link, or sensor name, use the full name printed
by `gz topic -l`.

## Bridge changes

### 1. Add configuration

Add a NavSat topic to the Gazebo section of `config/bridge.yaml`:

```yaml
gazebo:
  imu_topic: /imu
  altimeter_topic: /altimeter
  navsat_topic: /navsat
  actuator_topic: /X3/gazebo/command/motor_speed
```

The resolved topic must match the topic discovered with `gz topic -l`.

### 2. Subscribe and store one coherent sample

`GazeboStateSubscriber` should subscribe to `gz::msgs::NavSat`. Extend
`SensorSnapshot` with these six values:

```text
longitude_deg
latitude_deg
gps_altitude_m
velocity_east_m_s
velocity_north_m_s
velocity_up_m_s
```

Track NavSat readiness separately from IMU and altimeter readiness. Do not
send a GPS-enabled FDM packet until the first NavSat sample is available;
otherwise the initial zero latitude and longitude can become Betaflight's
home position.

### 3. Build the FDM packet

`FdmBuilder` should copy NavSat data according to the mapping table above.
It must not swap latitude and longitude, convert degrees to radians, or
convert ENU velocity to NED. Betaflight 2025.12.x expects longitude first and
the velocity components in ENU order.

Keep the existing barometer path:

- `position_xyz[2]` receives NavSat altitude above mean sea level.
- `pressure` continues to be generated by the configured pressure mode.
- The Gazebo altimeter can continue to supply the data used by that pressure
  path and by bridge diagnostics.

### 4. Handle the 2025.12 coordinate-direction issue explicitly

Betaflight 2025.12.x forwards the received latitude and longitude directly to
`setVirtualGPS()`. It does not contain the horizontal mirroring workaround
found in later Betaflight development versions.

Before enabling a correction in the bridge, perform the directional test in
the next section. If moving East makes longitude decrease, or moving North
makes latitude decrease, add a version-specific compatibility mode that
mirrors the readings around the first valid fix:

```text
corrected_longitude = 2 * origin_longitude - measured_longitude
corrected_latitude  = 2 * origin_latitude  - measured_latitude
```

Do not make this an undocumented unconditional transform. A newer Betaflight
version may already apply the same correction, in which case correcting in
both the bridge and Betaflight produces the wrong result again. A suitable
configuration name is:

```yaml
fdm:
  gps_coordinate_mode: betaflight_2025_12
```

## Betaflight setup

Use a SITL build from the `2025.12.x` release line. Its SITL target enables
the GPS feature and `USE_VIRTUAL_GPS`; no serial GPS receiver or NMEA/UBLOX
stream is needed. The bridge supplies GPS through the FDM packet on UDP 9003.

After starting Gazebo, SITL, and the bridge, query `MSP_RAW_GPS` through the
normal SITL MSP connection. The response should report a fix, satellites,
latitude, longitude, altitude, speed, and course. Betaflight Configurator may
also be used to inspect those values.

## Verification procedure

1. Start Gazebo and verify that `/navsat` publishes finite coordinates and
   ENU velocities.
2. Start Betaflight 2025.12.x and the bridge.
3. Confirm bridge status reports IMU, altimeter, and NavSat as ready and FDM
   packet count increases.
4. Confirm `MSP_RAW_GPS` reports a GPS fix with nonzero satellite count and
   coordinates close to the world's spherical origin.
5. Move the vehicle only along Gazebo +X (East). Longitude and
   `velocity_xyz[0]` must increase; course should be about 90 degrees.
6. Move it only along Gazebo +Y (North). Latitude and
   `velocity_xyz[1]` must increase; course should be about 0 degrees.
7. Move it upward. Altitude and `velocity_xyz[2]` must increase.
8. Stop NavSat updates and verify the intended stale-GPS behavior before
   relying on GPS Rescue or position-related modes.

## Acceptance criteria

- The bridge consumes `gz.msgs.NavSat` without changing the FDM packet size.
- Betaflight `2025.12.x` reports a virtual GPS fix through `MSP_RAW_GPS`.
- Longitude, latitude, altitude, speed, and course follow controlled movement
  in the expected directions.
- Existing IMU, barometer, motor, and FDM behavior remains operational.
- Coordinate correction is explicit and tied to the supported Betaflight
  compatibility mode.
